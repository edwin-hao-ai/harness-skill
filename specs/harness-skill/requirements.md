# Requirements Document: Harness Skill

## Introduction

Harness Skill is an interactive, interview-style skill for Kiro that guides users through creating a comprehensive "Harness Engineering" documentation system. The system generates cross-platform compatible Markdown documents that can be consumed by various AI agents (Claude, Codex, Cursor, Windsurf, Hermes, OpenClaw, etc.). The skill follows a progressive disclosure pattern, conducting interviews to gather project requirements and generating documents on-demand based on user needs.

## Glossary

- **Harness_Skill**: The Kiro skill that conducts interviews and generates the Harness Engineering documentation system
- **Harness_Map**: The central index file (`harness-map.md`) that serves as the navigation hub pointing to all other documents in the system
- **Harness_Engineering_System**: The complete documentation structure generated by Harness Skill, including all layered documents and agent entry points
- **Platform_Layer**: Base documents in `harness/platform/` including design.md, architecture.md, brain.md, voice.md, schema.md, prd.md, wireframe.md, prototype.md, search.md, glossary.md, constraints.md, and language.md
- **Domain_Layer**: Business logic documents in `harness/domain/` including domain-model.md, business-rules.md, use-cases.md, bugs.md, and todos.md
- **Application_Layer**: Implementation documents in `harness/application/` including project-structure.md, code-templates.md, test-strategy.md, and ci-cd.md
- **Interface_Layer**: User/external interaction documents in `harness/interface/` including user-guide.md, api-docs.md, and deployment.md
- **Memory_Layer**: Dynamic memory system in `memory/` with memory.md as index, decisions.md, and patterns.md
- **Agent_Entry_Point**: Files that provide instructions to AI agents (AGENTS.md, CLAUDE.md, .cursor/rules/, .windsurf/rules/)
- **Interview_Flow**: The multi-phase interactive process that gathers user requirements through structured questions
- **Interview_Phase**: A distinct stage in the interview process (Project Exploration, Agent Personality, Architecture, Prototype Specs)
- **User_Response**: The data collected from users during the interview process
- **Document_Generator**: The component responsible for creating Markdown documents based on collected responses
- **Voice_Enabled_Product**: A product that includes voice interface features, requiring voice.md generation
- **Progressive_Disclosure**: The pattern of revealing information and generating documents incrementally based on user needs
- **Cross_Agent_Compatibility**: The ability of generated documents to be consumed by multiple AI agent platforms

## Requirements

### Requirement 1: Skill Specification Compliance

**User Story:** As a Kiro developer, I want Harness Skill to follow the Kiro Skill specification, so that the skill integrates properly with Kiro's skill system.

#### Acceptance Criteria

1. THE Harness_Skill SHALL be defined in a SKILL.md file with valid YAML frontmatter
2. THE Harness_Skill SKILL.md SHALL include name, description, keywords, and version fields in the frontmatter
3. THE Harness_Skill SHALL follow the Agent Skills open standard format defined at agentskills.io
4. WHEN the SKILL.md file is parsed, THE Harness_Skill SHALL provide all required metadata fields
5. THE Harness_Skill SHALL be discoverable through Kiro's skill listing mechanism

---

### Requirement 2: Interview Flow Initialization

**User Story:** As a developer, I want to start the Harness Skill interview process with a clear introduction, so that I understand what to expect.

#### Acceptance Criteria

1. WHEN a user invokes Harness_Skill, THE Harness_Skill SHALL display an introduction explaining the purpose and scope of the documentation system
2. WHEN the introduction is displayed, THE Harness_Skill SHALL present the user with options to start the interview or learn more about each layer
3. WHEN the user chooses to start the interview, THE Harness_Skill SHALL begin with the Project Exploration phase
4. THE Harness_Skill SHALL maintain the current interview phase state throughout the session
5. IF the user interrupts the interview, THEN THE Harness_Skill SHALL preserve progress and allow resumption

---

### Requirement 3: Project Exploration Phase

**User Story:** As a developer, I want to provide my project goals and vision through guided questions, so that the generated documents reflect my project's needs.

#### Acceptance Criteria

1. WHEN the Project Exploration phase begins, THE Harness_Skill SHALL prompt the user for project name and description
2. AFTER receiving project name and description, THE Harness_Skill SHALL prompt for project goals and success criteria
3. AFTER receiving project goals, THE Harness_Skill SHALL prompt for target users and their primary use cases
4. AFTER receiving target users, THE Harness_Skill SHALL prompt for core features and prioritization
5. WHEN all Project Exploration questions are answered, THE Harness_Skill SHALL proceed to the Agent Personality phase
6. THE Harness_Skill SHALL validate that project name is non-empty before proceeding
7. IF the user provides incomplete responses, THEN THE Harness_Skill SHALL prompt for missing information

---

### Requirement 4: Agent Personality Phase

**User Story:** As a product manager, I want to optionally define the AI agent's personality, so that the generated voice.md reflects my product's tone.

#### Acceptance Criteria

1. WHEN the Agent Personality phase begins, THE Harness_Skill SHALL ask whether the product is voice-enabled
2. IF the product is voice-enabled, THEN THE Harness_Skill SHALL prompt for agent personality traits (tone, style, formality)
3. IF the product is voice-enabled, THEN THE Harness_Skill SHALL prompt for voice interaction patterns and response styles
4. IF the product is not voice-enabled, THEN THE Harness_Skill SHALL skip voice.md generation
5. THE Harness_Skill SHALL allow the user to skip individual personality questions with default values
6. WHEN Agent Personality questions are completed or skipped, THE Harness_Skill SHALL proceed to the Architecture phase

---

### Requirement 5: Architecture Phase

**User Story:** As a developer, I want to specify my technical stack and architecture preferences, so that the generated architecture.md reflects my project's structure.

#### Acceptance Criteria

1. WHEN the Architecture phase begins, THE Harness_Skill SHALL prompt for technology stack preferences (languages, frameworks, databases)
2. AFTER receiving technology stack, THE Harness_Skill SHALL prompt for architecture pattern preferences (monolith, microservices, serverless, etc.)
3. AFTER receiving architecture pattern, THE Harness_Skill SHALL prompt for deployment preferences (cloud provider, containerization)
4. AFTER receiving deployment preferences, THE Harness_Skill SHALL prompt for third-party integrations and dependencies
5. WHEN all Architecture questions are answered, THE Harness_Skill SHALL proceed to the Prototype Specs phase
6. THE Harness_Skill SHALL provide common technology stack options as suggestions
7. THE Harness_Skill SHALL allow free-form input for custom technology stacks

---

### Requirement 6: Prototype Specs Phase

**User Story:** As a developer, I want to specify my prototype output format preferences, so that the generated prototype.md uses my preferred format.

#### Acceptance Criteria

1. WHEN the Prototype Specs phase begins, THE Harness_Skill SHALL present output format options (HTML, Markdown, WireScript)
2. WHEN the user selects an output format, THE Harness_Skill SHALL prompt for prototype fidelity level (low-fidelity, high-fidelity)
3. AFTER receiving fidelity level, THE Harness_Skill SHALL prompt for component structure preferences
4. IF the user selects HTML format, THEN THE Harness_Skill SHALL prompt for CSS framework preferences
5. IF the user selects Markdown format, THEN THE Harness_Skill SHALL prompt for documentation style preferences
6. WHEN all Prototype Specs questions are answered, THE Harness_Skill SHALL present a summary for confirmation

---

### Requirement 7: Interview Summary and Confirmation

**User Story:** As a developer, I want to review my responses before document generation, so that I can correct any mistakes.

#### Acceptance Criteria

1. WHEN all interview phases complete, THE Harness_Skill SHALL present a comprehensive summary of all collected responses
2. THE Harness_Skill SHALL organize the summary by interview phase
3. THE Harness_Skill SHALL allow the user to navigate back to any phase to modify responses
4. WHEN the user confirms the summary, THE Harness_Skill SHALL begin document generation
5. IF the user requests changes, THEN THE Harness_Skill SHALL return to the specified phase for editing
6. THE Harness_Skill SHALL display the list of documents that will be generated based on responses

---

### Requirement 8: Harness Map Generation

**User Story:** As a developer, I want a central harness-map.md file, so that I have a single entry point to navigate all documentation.

#### Acceptance Criteria

1. WHEN document generation begins, THE Harness_Skill SHALL first generate the harness-map.md file
2. THE Harness_Skill SHALL generate harness-map.md with a table of contents organized by layer
3. THE Harness_Skill SHALL include relative path references to all generated documents in harness-map.md
4. THE Harness_Skill SHALL include a description for each document in harness-map.md
5. WHEN new documents are generated, THE Harness_Skill SHALL update harness-map.md to include references
6. THE Harness_Skill SHALL maintain alphabetical ordering within each layer section
7. THE Harness_Skill SHALL generate valid Markdown format for harness-map.md

#### Correctness Properties

1. **Reference Integrity**: FOR ALL document paths listed in harness-map.md, the referenced documents SHALL exist after generation is complete
2. **Path Validity**: FOR ALL paths in harness-map.md, the paths SHALL be valid relative paths from harness-map.md location
3. **Layer Completeness**: FOR EACH layer with generated documents, harness-map.md SHALL contain a section for that layer

---

### Requirement 9: Platform Layer Document Generation

**User Story:** As a developer, I want base documents in the Platform Layer, so that I have foundational design and architecture documentation.

#### Acceptance Criteria

1. WHEN generating Platform Layer documents, THE Harness_Skill SHALL create the `harness/platform/` directory
2. THE Harness_Skill SHALL generate design.md containing system design overview based on collected responses
3. THE Harness_Skill SHALL generate architecture.md containing technical architecture based on stack and pattern preferences
4. THE Harness_Skill SHALL generate brain.md containing cognitive model and decision-making context
5. THE Harness_Skill SHALL generate schema.md containing data models and schema definitions
6. THE Harness_Skill SHALL generate prd.md containing product requirements document
7. THE Harness_Skill SHALL generate glossary.md containing project-specific terminology
8. THE Harness_Skill SHALL generate constraints.md containing system constraints and limitations
9. WHERE voice-enabled product is indicated, THE Harness_Skill SHALL generate voice.md containing voice interaction specifications
10. THE Harness_Skill SHALL generate language.md based on language preferences
11. THE Harness_Skill SHALL generate wireframe.md containing UI wireframe specifications
12. THE Harness_Skill SHALL generate prototype.md in the selected output format
13. THE Harness_Skill SHALL generate search.md containing search functionality specifications

#### Correctness Properties

1. **Directory Structure**: THE `harness/platform/` directory SHALL exist after Platform Layer generation
2. **File Creation**: FOR EACH generated Platform Layer document, the file SHALL exist in `harness/platform/` directory
3. **Markdown Validity**: FOR EACH generated document, the content SHALL be valid Markdown format
4. **Conditional Generation**: IF voice-enabled is false, THEN voice.md SHALL NOT be generated
5. **Content Correlation**: FOR ALL generated documents, the content SHALL reference information collected during interviews

---

### Requirement 10: Domain Layer Document Generation

**User Story:** As a product manager, I want business logic documents in the Domain Layer, so that domain knowledge is captured and accessible.

#### Acceptance Criteria

1. WHEN generating Domain Layer documents, THE Harness_Skill SHALL create the `harness/domain/` directory
2. THE Harness_Skill SHALL generate domain-model.md containing entity definitions and relationships
3. THE Harness_Skill SHALL generate business-rules.md containing business logic rules and constraints
4. THE Harness_Skill SHALL generate use-cases.md containing user stories and use case descriptions
5. THE Harness_Skill SHALL generate bugs.md as a tracking document for known issues
6. THE Harness_Skill SHALL generate todos.md as a tracking document for pending tasks
7. THE Harness_Skill SHALL populate use-cases.md based on target users and core features collected in Project Exploration

#### Correctness Properties

1. **Directory Structure**: THE `harness/domain/` directory SHALL exist after Domain Layer generation
2. **Use Case Mapping**: FOR EACH core feature collected in interviews, use-cases.md SHALL contain at least one corresponding use case
3. **Markdown Validity**: FOR EACH generated Domain Layer document, the content SHALL be valid Markdown format

---

### Requirement 11: Application Layer Document Generation

**User Story:** As a developer, I want implementation documents in the Application Layer, so that I have technical guidance for development.

#### Acceptance Criteria

1. WHEN generating Application Layer documents, THE Harness_Skill SHALL create the `harness/application/` directory
2. THE Harness_Skill SHALL generate project-structure.md containing directory structure and file organization
3. THE Harness_Skill SHALL generate code-templates.md containing reusable code patterns and templates
4. THE Harness_Skill SHALL generate test-strategy.md containing testing approach and coverage requirements
5. THE Harness_Skill SHALL generate ci-cd.md containing continuous integration and deployment pipelines
6. THE Harness_Skill SHALL populate project-structure.md based on architecture pattern preferences

#### Correctness Properties

1. **Directory Structure**: THE `harness/application/` directory SHALL exist after Application Layer generation
2. **Architecture Alignment**: THE project-structure.md content SHALL reflect the architecture pattern selected during interviews

---

### Requirement 12: Interface Layer Document Generation

**User Story:** As a developer, I want interaction documents in the Interface Layer, so that user and API documentation is available.

#### Acceptance Criteria

1. WHEN generating Interface Layer documents, THE Harness_Skill SHALL create the `harness/interface/` directory
2. THE Harness_Skill SHALL generate user-guide.md containing end-user documentation
3. THE Harness_Skill SHALL generate api-docs.md containing API endpoint documentation
4. THE Harness_Skill SHALL generate deployment.md containing deployment instructions and procedures
5. THE Harness_Skill SHALL populate user-guide.md based on target users and core features collected

#### Correctness Properties

1. **Directory Structure**: THE `harness/interface/` directory SHALL exist after Interface Layer generation
2. **User Alignment**: THE user-guide.md content SHALL reference target users defined during Project Exploration

---

### Requirement 13: Memory Layer Document Generation

**User Story:** As a developer, I want a dynamic memory system in the Memory Layer, so that context and decisions are preserved across sessions.

#### Acceptance Criteria

1. WHEN generating Memory Layer documents, THE Harness_Skill SHALL create the `memory/` directory
2. THE Harness_Skill SHALL generate memory.md as the memory index file
3. THE Harness_Skill SHALL generate decisions.md containing architectural and design decisions
4. THE Harness_Skill SHALL generate patterns.md containing identified patterns and best practices
5. THE memory.md file SHALL reference decisions.md and patterns.md
6. THE Harness_Skill SHALL populate decisions.md with initial decisions made during the interview

#### Correctness Properties

1. **Directory Structure**: THE `memory/` directory SHALL exist after Memory Layer generation
2. **Memory Index Integrity**: THE memory.md file SHALL contain valid references to decisions.md and patterns.md

---

### Requirement 14: Agent Entry Point Generation

**User Story:** As a team, we want cross-platform compatible agent instructions, so that any AI agent can work with our Harness Engineering system.

#### Acceptance Criteria

1. WHEN generating Agent Entry Points, THE Harness_Skill SHALL generate AGENTS.md as the universal agent instruction file
2. THE Harness_Skill SHALL generate CLAUDE.md for Claude-specific instructions
3. THE Harness_Skill SHALL create the `.cursor/rules/` directory and generate Cursor-specific rule files
4. THE Harness_Skill SHALL create the `.windsurf/rules/` directory and generate Windsurf-specific rule files
5. THE AGENTS.md file SHALL reference harness-map.md as the primary navigation entry point
6. THE CLAUDE.md file SHALL reference harness-map.md and include Claude Code memory integration
7. THE Harness_Skill SHALL generate platform-specific instruction files that reference the harness-map.md
8. FOR EACH generated Agent Entry Point file, the content SHALL include instructions for AI agents to locate and use the Harness Engineering system

#### Correctness Properties

1. **Harness Map Reference**: FOR EACH Agent Entry Point file, the content SHALL contain a reference to harness-map.md
2. **File Existence**: AFTER generation, AGENTS.md, CLAUDE.md, .cursor/rules/, and .windsurf/rules/ SHALL exist
3. **Cross-Agent Compatibility**: THE AGENTS.md content SHALL use syntax compatible with multiple AI agent platforms

---

### Requirement 15: Progressive Document Generation

**User Story:** As a developer, I want documents generated incrementally, so that I can start using partial output without waiting for full generation.

#### Acceptance Criteria

1. WHEN document generation begins, THE Harness_Skill SHALL generate the harness-map.md first
2. AFTER harness-map.md is generated, THE Harness_Skill SHALL generate Platform Layer documents
3. AFTER Platform Layer documents are generated, THE Harness_Skill SHALL generate Domain Layer documents
4. AFTER Domain Layer documents are generated, THE Harness_Skill SHALL generate Application Layer documents
5. AFTER Application Layer documents are generated, THE Harness_Skill SHALL generate Interface Layer documents
6. AFTER Interface Layer documents are generated, THE Harness_Skill SHALL generate Memory Layer documents
7. AFTER all layer documents are generated, THE Harness_Skill SHALL generate Agent Entry Points
8. THE Harness_Skill SHALL update harness-map.md after each layer completes
9. THE Harness_Skill SHALL provide progress updates during generation

#### Correctness Properties

1. **Generation Order**: THE harness-map.md SHALL be generated before any layer documents
2. **Progressive Updates**: FOR EACH layer completion, harness-map.md SHALL be updated to reference the newly generated documents

---

### Requirement 16: Cross-Agent Compatibility

**User Story:** As a developer, I want generated documents to work with multiple AI agent platforms, so that my team can use different AI tools with the same documentation.

#### Acceptance Criteria

1. THE Harness_Skill SHALL generate all documents in standard Markdown format
2. THE Harness_Skill SHALL avoid platform-specific Markdown extensions
3. THE Harness_Skill SHALL use relative paths for internal document references
4. THE Harness_Skill SHALL include clear section headers using standard Markdown heading syntax
5. THE Harness_Skill SHALL generate AGENTS.md with instructions that work across Claude, Codex, Cursor, Windsurf, Hermes, and OpenClaw
6. WHEN generating code examples in documents, THE Harness_Skill SHALL use fenced code blocks with language identifiers

#### Correctness Properties

1. **Markdown Standards Compliance**: FOR ALL generated Markdown files, the content SHALL conform to CommonMark specification
2. **Path Portability**: FOR ALL internal document references, the paths SHALL be relative and valid from any document location
3. **Code Block Format**: FOR ALL code examples, fenced code blocks SHALL include valid language identifiers

---

### Requirement 17: Interview State Persistence

**User Story:** As a developer, I want to resume an interrupted interview, so that I don't lose my progress if I need to stop mid-process.

#### Acceptance Criteria

1. WHEN the user interrupts an interview, THE Harness_Skill SHALL save the current interview state
2. THE Harness_Skill SHALL save interview state to a `.harness-skill-state.json` file in the project root
3. WHEN the user resumes the interview, THE Harness_Skill SHALL detect existing state and offer to continue
4. IF the user chooses to continue, THE Harness_Skill SHALL restore all previous responses
5. IF the user chooses to start over, THE Harness_Skill SHALL clear the saved state
6. THE Harness_Skill SHALL remove the state file after successful document generation

#### Correctness Properties

1. **State File Validity**: THE `.harness-skill-state.json` file SHALL contain valid JSON structure
2. **State Completeness**: THE saved state SHALL include all responses from all completed phases
3. **Round-Trip Integrity**: WHEN state is saved and restored, the restored state SHALL equal the original state

---

### Requirement 18: Document Template System

**User Story:** As a developer, I want documents generated from templates, so that the output follows consistent structure and formatting.

#### Acceptance Criteria

1. THE Harness_Skill SHALL use templates for each document type
2. THE Harness_Skill SHALL populate template placeholders with collected user responses
3. THE Harness_Skill SHALL use consistent heading hierarchy across all generated documents
4. THE Harness_Skill SHALL include standard sections in each document type (Introduction, Overview, Details)
5. THE Harness_Skill SHALL allow template customization for advanced users

#### Correctness Properties

1. **Placeholder Resolution**: FOR EACH template placeholder, the generated document SHALL have the placeholder replaced with actual content
2. **Structure Consistency**: FOR documents of the same type, the heading hierarchy SHALL be consistent

---

### Requirement 19: Error Handling and Recovery

**User Story:** As a developer, I want clear error messages and recovery options, so that I can resolve issues without losing work.

#### Acceptance Criteria

1. IF an error occurs during interview, THE Harness_Skill SHALL display a descriptive error message
2. IF an error occurs during document generation, THE Harness_Skill SHALL preserve successfully generated documents
3. IF an error occurs during document generation, THE Harness_Skill SHALL offer to retry or skip the failed document
4. IF file system permissions prevent document creation, THE Harness_Skill SHALL display a clear permission error
5. IF the user provides invalid input, THE Harness_Skill SHALL display validation errors and re-prompt

#### Correctness Properties

1. **Partial Output Preservation**: IF generation fails mid-process, THEN all documents generated before the failure SHALL remain on disk
2. **Error Message Clarity**: FOR ALL error conditions, the error message SHALL describe the problem and suggest corrective action

---

### Requirement 20: Help and Documentation

**User Story:** As a developer, I want access to help information during the interview, so that I understand what each question is asking.

#### Acceptance Criteria

1. WHEN the user requests help, THE Harness_Skill SHALL display context-sensitive help for the current question
2. THE Harness_Skill SHALL provide examples for each interview question
3. THE Harness_Skill SHALL include a help command that lists all available commands
4. THE Harness_Skill SHALL provide documentation about each document type and its purpose
5. WHEN displaying help, THE Harness_Skill SHALL maintain the current interview position

## Non-Functional Requirements

### NFR-1: Performance

1. THE Harness_Skill SHALL respond to user input within 2 seconds
2. THE Harness_Skill SHALL generate each document within 5 seconds
3. THE Harness_Skill SHALL complete full document generation for a standard project within 60 seconds

### NFR-2: Usability

1. THE Harness_Skill SHALL use clear, non-technical language in interview questions
2. THE Harness_Skill SHALL provide sensible default values where appropriate
3. THE Harness_Skill SHALL allow the user to skip optional questions

### NFR-3: Maintainability

1. THE Harness_Skill SHALL follow the SKILL.md specification version 1.0
2. THE Harness_Skill SHALL use modular document templates
3. THE Harness_Skill SHALL log interview sessions for debugging purposes

### NFR-4: Compatibility

1. THE Harness_Skill SHALL be compatible with Kiro IDE
2. THE Harness_Skill SHALL generate documents compatible with UTF-8 encoding
3. THE Harness_Skill SHALL work on macOS, Windows, and Linux platforms

---

## Constraints

1. THE Harness_Skill SHALL NOT require internet connectivity for core functionality
2. THE Harness_Skill SHALL NOT collect or transmit user data externally
3. THE Harness_Skill SHALL NOT modify files outside the project directory without explicit user consent
4. THE Harness_Skill SHALL NOT overwrite existing documents without user confirmation

---

## Dependencies

1. THE Harness_Skill depends on Kiro's skill execution environment
2. THE Harness_Skill depends on file system write access for document generation
3. THE Harness_Skill depends on UTF-8 encoding support for cross-platform compatibility
