# Design Doc · TaskFlow

> 工程设计文档（Google 风格）：**约束实现方式**，记录关键决策、约束程度与备选方案。
> 产品需求见 [spec.md](spec.md)；落定后的架构速查见 [architecture.md](architecture.md)。

## Context & Scope

TaskFlow 的产品赌注（见 [spec.md](spec.md)）是"用一块**实时、可信**的看板取代每日同步会"。
"可信"这个词把两件事抬成了技术级硬约束：**任务状态变更要近实时地对全队可见**，且**并发更新不能
彼此覆盖**。一旦看板与现实不符，整个产品的前提就崩了。本设计覆盖支撑这一点的技术方案，不覆盖产品
需求本身。

## Goals / Non-Goals（技术）

**Goals**

- 任务状态变更对同看板其他成员的可见延迟 < 2s（支撑"取代会议"）。
- 两人并发移动同一任务时，不发生"后写覆盖先写"且用户能感知冲突。
- MVP 可在单台机器上跑起来，部署与运维成本接近于零。

**Non-Goals**

- 不追求水平扩展到大型组织（见架构模式决策）。
- 不做离线优先（offline-first）的完整 CRDT 合并——本期用乐观更新 + 冲突提示即可。

## 提议的设计

- **架构模式**：单体（Monolith），领域逻辑按 `modules/` 切分，预留未来拆分接缝。
- **实时通道**：任务变更经领域事件 → WebSocket 广播（`task.moved` / `task.commented`），
  客户端订阅自己所在看板；前端做乐观更新，服务端确认后对账。
- **并发控制**：`Task` 行带 `version` 乐观锁，更新 `WHERE version = ?`，未命中返回 409。
- 核心数据流与数据模型草图见 [architecture.md](architecture.md)。

## Degree of Constraint（约束程度）

| 维度 | 约束 | 说明 |
| --- | --- | --- |
| 强一致的任务状态 | **硬约束** | 看板可信的前提，不得用最终一致替代。 |
| 乐观锁 + 409 冲突语义 | **硬约束** | 任何写路径都必须走，否则并发会破坏看板。 |
| 实时通道的具体实现 | 可裁量 | WebSocket 优先；MVP 可短轮询兜底，但须记为技术债。 |
| 模块内部实现 / 次要库 | 可裁量 | 留给实现者。 |

## Alternatives Considered（备选方案）

- **微服务而非单体**：拒绝。团队小、领域单一，拆分只换来跨服务事务与部署复杂度；而"看板可信"需要
  强一致，跨服务最终一致会把核心卖点置于风险。保留按模块拆分的接缝即可，无需现在拆。
- **纯 REST 短轮询而非 WebSocket**：作为 MVP 兜底可接受，但长期拒绝——轮询的延迟与额外负载直接削弱
  "实时可信"。若先用轮询，必须在 decisions 里记为待偿技术债。
- **悲观锁（行锁）而非乐观锁**：拒绝。看板是高并发读、偶发并发写，悲观锁会拖慢常见路径；乐观锁在
  低冲突场景成本更低，且能给用户清晰的"刚被他人更新"反馈。

## Cross-Cutting Concerns

### 安全 / 隐私

- 任务与评论按 `team_id` 隔离，任何查询都必须带团队作用域，杜绝越权读写。
- Slack token 等密钥走环境变量/密钥管理，不入库明文、不进日志。

### 可观测性

- 关键事件（任务移动、冲突 409、Slack 推送失败）打结构化日志 + 计数指标，便于定位"看板不同步"投诉。

### 发布 / 回滚

- **云服务商**：AWS
- **容器化**：Docker（单镜像，符合单体定位）
- **CI/CD**：GitHub Actions（push → 测试 → 构建镜像 → 部署）；回滚即重部署上一镜像。

## Open Questions

- 通知聚合策略：高频评论是否每条都推 Slack？本期先仅 `@` 才推，聚合留待数据反馈后再定。
- 任务删除时评论如何处理：倾向软删除任务、保留评论（审计价值），待确认。
