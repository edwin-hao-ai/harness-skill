# Use Cases · TaskFlow

> 覆盖 2 个核心功能；主要角色：团队负责人（隐含执行成员，见 [Design](../platform/design.md)）。

## UC-01: 任务看板（高优先级）

- **主要角色**：团队负责人（创建/分配）、执行成员（更新状态）
- **目标**：让全队任务状态在一块看板上保持实时可信，无需口头同步。

**主流程：**

1. 负责人新建任务，填标题、指派成员、设优先级，任务落在「待办」列。
2. 成员开始处理，把任务从「待办」拖到「进行中」——拖拽即时生效（乐观更新）。
3. 服务端确认并通过 WebSocket 广播 `task.moved`，其他成员的看板即时刷新。
4. 完成后拖到「完成」，触发 Slack 通知给负责人。

**边界与异常：**

- **并发移动**：两人几乎同时移动同一任务 → 乐观锁 version 不命中者收到 409，看板自动拉新并提示
  "该任务刚被他人更新"（见 [Architecture](../platform/architecture.md) 并发写冲突）。
- **离线/弱网**：拖拽已本地生效但服务端确认失败 → 回滚该卡片并标记"未同步"，不静默丢更新。
- **空看板**：首次进入应有引导（"创建第一个任务"），否则负责人不知从何下手。

## UC-02: 任务评论（中优先级）

- **主要角色**：负责人与成员
- **目标**：把原本要开会说的卡点、决策沉淀到任务下，实现异步对齐。

**主流程：**

1. 成员在任务卡打开详情，发表评论说明卡点（如"等设计稿"）。
2. `@` 负责人 → 触发 Slack 通知，把人拉回上下文。
3. 负责人在评论里答复或重新指派，讨论与任务天然绑定，事后可追溯。

**边界与异常：**

- **被删任务的评论**：任务删除时评论如何处理 → 建议软删除任务并保留评论，因为决策记录有审计价值。
- **通知风暴**：高频评论不应每条都推 Slack → 需做聚合/免打扰（记为待办，本期可简化为仅 `@` 才推）。
