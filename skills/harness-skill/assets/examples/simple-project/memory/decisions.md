# Decisions · TaskFlow

> 初始决策来自访谈与由其推导的设计。后续按时间追加。

## D-001: 采用单体架构

**决策**：MVP 用单体，不上微服务。
**理由**：团队小、领域单一；"看板可信"需要强一致，单库单进程最稳；按 `modules/` 切分预留拆分接缝。
**代价**：单点伸缩；可接受。

## D-002: 技术栈全 TypeScript

**决策**：前 React / 后 Express / 库 PostgreSQL，语言统一 TypeScript。
**理由**：`Task`/`Status`/`version` 等领域类型前后端共享，消除契约漂移；看板重交互，React 组件化+乐观更新是体验基础。

## D-003: 实时同步用 WebSocket，乐观锁解决并发

**决策**：变更走 WebSocket 广播 + 前端乐观更新；任务行带 `version` 乐观锁，冲突返回 409。
**理由**：直接服务"砍掉同步会"的目标——看板必须实时且不被并发写覆盖。
**已知债**：MVP 若先用 3–5s 短轮询兜底，须尽快换 WebSocket，否则削弱核心卖点。

## D-004: 本期以负责人为中心，但数据模型预留成员角色

**决策**：文档与功能聚焦团队负责人；`User.role` 预留 `lead|member`。
**理由**：访谈只显式提到负责人，但产品成立必然有执行成员；现在不做成员专属功能，但模型不能挡路。

## D-005: Slack 通知走异步队列

**决策**：分配/状态变更/被 @ 推 Slack，但经异步队列，不在看板主请求里同步调用。
**理由**：避免 Slack 抖动拖慢看板；通知是"用户离开看板时"的触达补充。
